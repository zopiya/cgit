# 单容器 SSH 与仓库权限方案（待确认，未实现）

> 已由 [完整一体化规划](PLAN.md) 接续：用户现已接受容器或 Compose，推荐结构改为同一 Compose 内的 edge/web/ssh。本文保留为前一轮讨论记录；“必须单容器”和“HTTPS 范围待回答”不再是当前规划前提。人员权限、SSH/LFS 等目标以 PLAN.md 为准，均尚未实现。

目标：个人托管与少量协作者共享。网页、Git HTTP、Git SSH、Git LFS 都在同一容器内，不使用宿主机 SSH 或 Git 服务。不加入注册、组织、PR/Issue、复杂角色或网页管理平台。

这是下一阶段设计，不代表当前功能。当前仍是全站 public/private、单 HTTP 账号、宿主机 SSH 独立管理；上一批本地修复尚未部署。

## 身份和授权

一个人对应一个服务身份，可以登记多把设备公钥；多人不共用私钥、HTTP 密码或 token。SSH 使用统一的 Git 系统账号，按公钥识别具体人员，不要求每人一个 Linux 账号。

| 身份/授权 | 公开仓库读取 | 私有仓库读取 | 推送 Git / 上传 LFS | 建库、删库、改授权 |
|---|---|---|---|---|
| 访客 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 只读协作者 | 允许 | 仅明确授权的仓库 | 拒绝 | 拒绝 |
| 读写协作者 | 允许 | 仅明确授权的仓库 | 仅明确授权的仓库 | 拒绝 |
| 所有者 | 允许 | 全部 | 全部 | 通过管理配置/容器管理命令 |

账号登记不等于自动获得私有仓库权限。读写包含读取；未匹配规则拒绝。公开意味着匿名可读，不意味着匿名可写。新增仓库默认私有，只能由所有者明确发布。

仓库可见性和人员授权采用一份声明式配置作为权威，管理者维护身份、公钥、公开标志、读者和写者；HTTP 凭证另存秘密文件。撤销人员或权限时，后续 SSH、HTTP、网页和 LFS 请求都应拒绝，短期 token 不得绕过当前授权。

仓库级读写不等于分支保护：基础推送权限涉及分支/标签更新，强推与删除策略需在实施前明确，不能暗示已拥有 Forgejo 的受保护分支、审核或合并规则。

## 请求入口

- SSH：容器内 OpenSSH 验证公钥，固定命令入口只接收允许的 Git 操作及 LFS 认证请求。禁止交互终端、端口/agent/X11 转发和其他系统命令；不能用 eval 或把原始命令交给 shell 执行。
- Web：按当前访问者生成可见仓库列表，并对每个直链和旧 query-string 入口重新授权。未授权仓库不显示名称、描述和活动信息。`cgit.hide` 只属于展示选项，不参与身份授权。
- Git HTTP：使用各自 HTTP 凭证识别身份，按同一规则放行读取和推送。保留传输总开关，但开关开启不能越过仓库 ACL。
- LFS：读取权限对应下载，写入权限对应上传/verify。对象直链、Range、raw、README 图片和预览同样授权，不能只保护 Batch 请求。

浏览器不会自动利用 SSH 公钥登录。私有网页采用独立的每人 HTTP 凭证；Git SSH 使用公钥，二者关联到同一个服务身份。首版不做注册、找回密码或用户管理页面。

## LFS 内置的含义

cgit 原生没有 Git LFS。当前项目已经在容器内实现 HTTP Batch + Basic transfer，不需要外部 LFS 服务；保留独立 `/lfs` 数据目录。

计划补充 `git-lfs-authenticate`：客户端使用 SSH 公钥确认身份后，服务返回 HTTPS LFS 地址和短期凭证。凭证至少绑定身份、仓库、upload/download 操作和有效期；HTTP 网关在 Batch 和对象 action 上都验证范围，并检查当前授权。凭证不记入访问日志或仓库文件。

这是“SSH 认证 + HTTPS 传输 LFS”，不是纯 SSH 大文件传输。客户端仍需要 Git LFS。暂不扩展锁、自动 GC 或归档内展开 LFS。

## 单容器运行和持久化

容器同时包含 Web 服务、SSH 服务、Git 后端、LFS 和权限入口。加入 SSH 后无法再只 exec 一个 lighttpd；需要简单的进程管理，负责信号、退出、子进程回收及健康检查，避免 SSH 已死但容器仍显示健康。

持久数据包括：

- Git 仓库与 LFS 对象，沿用现有布局。
- 人员/仓库权限配置、公钥和 HTTP 凭证。
- SSH 主机私钥；重建容器后保持相同指纹，必须独立持久化和备份。
- 若内置 Caddy，再持久化其证书状态。token 签名秘密如采用，也需要受控保存与轮换。

容器 SSH 端口和宿主机管理 SSH 分开映射，不更改宿主机的 SSH 配置。用户只向 Git 容器提供公钥，不把个人私钥放进容器。

“HTTPS 是否也在同一容器”待用户回答。若包括，则公网 TLS 入口也必须内置；若不包括，可接已有 HTTPS 入口。不能在用户要求单容器时默认另起一套代理服务。

## 实现取舍和验证

OpenSSH 与 Git 负责成熟协议；授权层可评估复用 Gitolite 等现有实现。Gitolite 的 SSH 授权并不自动完成 cgit/LFS 的统一授权，不能仅安装它就宣称全部入口安全。具体后端尚未选定，避免先写两套不同规则。

这比现在的单账号网关更复杂：增加配置、进程管理和权限验证责任。只承诺仓库级访问和少量协作，不以“轻量”为由省略跨入口检查。

按增量实施：

1. 统一人员/仓库模型及默认拒绝规则，明确旧全站账号如何兼容，保留现有数据，不自动公开任何仓库。
2. 接入 Web、Git HTTP 和 LFS 权限，包括列表、直链、归档及缓存隔离。
3. 增加容器 SSH、公钥身份与强制命令入口，补 SSH LFS 认证。
4. 验证所有者、只读、读写、访客及被撤销人员，在公开/私有仓库上的网页、SSH、HTTP、LFS 允许与拒绝行为；权限变更后旧凭证不能继续访问。
5. 以真实容器验证启停、重启、SSH 指纹保持、异常进程退出、数据备份恢复、原有 Git/LFS 功能和 HTTPS 地址。完成后才安排 NAS/VPS 部署。

本机目前无 Docker；容器验证是交付缺口，不能拿 Python 单元测试替代。未授权前不操作 NAS/VPS、不提交或发布。
